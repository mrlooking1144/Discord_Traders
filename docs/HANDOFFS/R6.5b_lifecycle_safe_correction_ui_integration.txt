    TradeService.correct_trade_signal(
        selected["id"],
        expected_current_values=expected_values,

    TradeService.update_trade_signal(...)

# 7. Transaction Ownership

`correct_trade_signal()` owns the complete correction transaction end to
end via the pre-existing `TradeService._r5_write_transaction()` context
manager (unchanged from R6.5a): it commits exactly once on success and
rolls back the entire operation on any failure.

The correction-save branch in `app/streamlit_app.py` no longer calls
`conn.commit()` or `conn.rollback()` at any point - all four such calls
that existed in the pre-R6.5b UI (one success-path commit, three
per-exception-branch rollbacks) were removed. Verified via static
search: the only executable `conn.commit()`/`conn.rollback()` calls
remaining in `app/streamlit_app.py` are the three inside the Manual
Message Entry Submit workflow (its own separate, caller-owned ingestion
transaction, entirely unrelated to and unchanged by this milestone). A
fourth textual match exists only inside this module's own docstring
prose describing this exact invariant - not executable code.

# 8. Exception-to-Message Mapping

Validation message (form remains open, state preserved):

    Please enter a valid correction that changes at least one field.

Used for:
    - missing confirmation (client-side, before any service call);
    - malformed client input - unparseable price or expiration
      (client-side, before any service call);
    - a no-op correction rejected by the service (plain `ValueError`);
    - `LifecycleUnsafeCorrectionError` (a new R6.5a exception - raised
      when a requested correction would change `action` on a
      lifecycle-managed signal);
    - any other expected correction-validation `ValueError` case.

Conflict message (form remains open, state preserved):

    This trade signal changed or is no longer available. Reload it
    before correcting.

Used for:
    - `StaleTradeSignalError`;
    - `TradeSignalNotFoundError`.

    (This is the one message whose state-clearing behavior CHANGED in
    R6.5b - see section 9.)

Generic failure message (form remains open, state preserved; the UI
never calls `conn.rollback()` for any of these, since
`correct_trade_signal()` has already rolled back internally before this
exception propagates):

    Could not save the trade signal correction.

Used for:
    - `LifecycleIntegrityError` (a new R6.5a exception);
    - `LifecycleSnapshotError` (a new R6.5a exception);
    - `TypeError`;
    - `sqlite3.Error`;
    - `OSError`;
    - `RuntimeError`;
    - any other unexpected exception (bare `except Exception`).

Success message:

    Trade signal correction saved.

Audit-history failure message (unchanged, unrelated to the Save-
Correction path - covers `list_trade_signal_audit_history()` failures):

    Could not load correction history.

All five messages are byte-for-byte identical to their pre-R6.5b
(Milestone 2D.5) text - none of the approved user-facing strings were
altered.

Exception-catch ordering in the implementation (most specific first, so
no subclass is swallowed by a broader `except`): `(StaleTradeSignalError,
TradeSignalNotFoundError)` -> `LifecycleUnsafeCorrectionError` -> plain
`ValueError` -> `(LifecycleIntegrityError, LifecycleSnapshotError,
TypeError, sqlite3.Error, OSError, RuntimeError)` -> bare `Exception`.

# 9. Correction-State Behavior

Correction form state and every entered widget value are now preserved
after EVERY rejected save:

    - missing confirmation;
    - malformed client-side input (symbol, price, or expiration);
    - a no-op correction;
    - a lifecycle-unsafe action correction (`LifecycleUnsafeCorrectionError`);
    - a stale-value conflict (`StaleTradeSignalError`);
    - a signal-not-found conflict (`TradeSignalNotFoundError`);
    - a lifecycle-integrity failure (`LifecycleIntegrityError`);
    - a lifecycle-snapshot failure (`LifecycleSnapshotError`);
    - a type failure (`TypeError`);
    - a database failure (`sqlite3.Error`);
    - an OS failure (`OSError`);
    - a runtime failure (`RuntimeError`);
    - any other unexpected failure.

This is a deliberate behavior CHANGE from the pre-R6.5b (Milestone 2D.5)
UI for exactly one category: a stale-value or not-found conflict
previously cleared `correction_signal_id`/`correction_expected_values`
from `st.session_state` (forcing the user to re-open the form from
scratch); R6.5b removes those two `st.session_state.pop()` calls from
that exception branch, so a conflict now behaves like every other
rejection - the form and the user's in-progress edits stay exactly as
entered.

Correction state clears ONLY after:

    1. A successful save.
    2. An explicit Cancel.
    3. A change of the selected signal (a different signal ID chosen in
       the review selectbox).
    4. A filter change that removes the currently-selected signal from
       the visible result set.

No other event clears correction state. These four clearing paths were
already correctly implemented before R6.5b for cases 2-4 (Cancel,
signal-selection change, filter-removal all predate this milestone
unchanged); R6.5b's only state-management change is removing the
premature clearing from the conflict branch described above.

# 10. Fixed-Choice Compatibility Correction

Confirmed prior defect: the Recovery-track extractor
(`app/parser.py`'s `extract_trade_event()`, used by
`TradeService.ingest_channel_message()`/`ingest_batch()`) persists
actions including `BOUGHT` and `SOLD`
(`_EXTRACTOR_ACTION_RE = r"^(BOUGHT|SOLD|BTO|STC|BTC|STO|BUY|SELL)$"`),
stored verbatim and never aliased
(`TradeSignal.action`'s own docstring: "stored exactly as supplied and
never aliased"). The pre-R6.5b UI's fixed `_ACTION_CHOICES = ["BTO",
"STC", "BTC", "STO", "BUY", "SELL"]` list omitted both. Its selectbox
index-selection logic fell back to index 0 whenever the persisted action
was not in that list:

    action_index = (
        _ACTION_CHOICES.index(current_action)
        if current_action in _ACTION_CHOICES
        else 0
    )

For a persisted `"BOUGHT"` signal, this rendered `"BTO"` as the visibly
selected action with no indication the true stored value differed. A
user correcting only price, expiration, or another unrelated field -
without touching the action dropdown - would submit `action_input ==
"BTO"` as part of `changed_fields`, silently converting `BOUGHT` -> `BTO`
(or, symmetrically, `SOLD` -> `STC`) on save.

Implemented solution: a new pure helper,
`_correction_selectbox_choices(base_choices, current_value)`, builds a
FRESH copy of `base_choices` and appends `current_value` only when it is
not already present:

    def _correction_selectbox_choices(base_choices, current_value):
        choices = list(base_choices)
        if current_value not in choices:
            choices.append(current_value)
        return choices

The action selectbox's options and default index are now built from
this helper's fresh list, with `index=action_choices.index(current_action)`
(guaranteed present, since the helper appended it if absent) -
eliminating the index-0 fallback entirely. The standard six action
choices remain unchanged and always present; `_ACTION_CHOICES` itself is
never mutated (`list(base_choices)` always creates a fresh copy). No
normalization or aliasing was introduced - `BOUGHT` is never mapped to
`BTO`, `SOLD` is never mapped to `STC` - and no free-text action entry
was added; the field remains a fixed `st.selectbox`.

The identical defensive pattern is applied to `option_type`
(`_OPTION_TYPE_CHOICES = ["", "call", "put"]`): a persisted `option_type`
outside that set is appended and selected by default, never silently
replaced. `option_type` is documented as free-text
(`TradeSignal.option_type`'s docstring: "Free-text call/put, or None for
non-option trades") and is not constrained to an enum by
`validate_trade_signal_update_fields()` at the repository layer, so
while today's extractor grammars only ever produce `None`/`"call"`/
`"put"`, this defensive branch guards against a value outside that set
reaching the UI through any future write path.

Verified via real signals in both the AppTest suite (`tests/test_app.py`)
and the real-SQLite integration suite
(`tests/test_correction_integration.py`): a persisted `BOUGHT` action is
offered in the selectbox, selected by default, and submitted unchanged
on a price-only correction (`call.kwargs["action"] == "BOUGHT"`, never
`"BTO"`); identical coverage exists for `SOLD` and for an out-of-list
`option_type` value.

# 11. Lifecycle Behavior

All lifecycle behavior below is exactly the R6.5a `correct_trade_signal()`
contract (unmodified by R6.5b) - R6.5b only changes how the UI invokes
it. Verified through the UI this milestone via real-SQLite integration
tests (`LifecycleAwareUiCorrectionIntegrationTests`), not merely at the
service layer:

    - A price-only (or other non-key-field) correction of a lifecycle-
      managed signal is supported through the UI and never triggers a
      rebuild.
    - A lifecycle-key correction (symbol, option_type, or expiration)
      submitted through the UI triggers a targeted lifecycle rebuild for
      the corrected signal's raw_message_id.
    - The old lifecycle generation is superseded (`is_current` cleared)
      as part of that rebuild.
    - The corrected signal's `lifecycle_id` pointer is reloaded post-
      rebuild and points to the new (replacement) lifecycle generation.
    - No dual current lifecycle membership remains for the affected
      raw_message_id after a UI-driven correction -
      `get_current_lifecycle_ids_for_raw_message_ids()` returns exactly
      one id (the new generation's).
    - `validate_lifecycle_membership_integrity()` reports zero
      violations after every UI-driven correction in the test suite.
    - A managed `action` change submitted through the UI (i.e. `action`
      would effectively change on a signal with `event_type IS NOT
      NULL`) is rejected atomically with `LifecycleUnsafeCorrectionError`,
      surfaced through the UI as the validation message.
    - A rejected correction (of any kind, including the managed-action
      case) creates no partial mutation whatsoever - no signal-column
      change, no audit row, no lifecycle supersession, no lifecycle
      creation, no lifecycle-event insert, and no lifecycle-id pointer
      change - proven via full before/after state snapshots
      (`trade_signals`, `trade_signal_edits`, `trade_lifecycles`,
      `trade_lifecycle_events` row counts and content, all byte-for-byte
      unchanged) in the real-SQLite rejection test.

# 12. Logging and Privacy

Correction failures continue to route through the existing sanitized
`log_operation_failure(logger, "trade signal correction", exc)` contract
(unchanged) for every one of the new exception categories introduced by
R6.5b, exactly as they did before. Verified this milestone (both by
direct code inspection and by `assertLogs`-based tests) that no log
record produced by the correction path ever contains:

    - raw message text;
    - entered correction values (symbol, price, expiration, position
      size, action, or option type text the user typed);
    - trader identifiers;
    - database or log paths;
    - exception message text (only the exception CLASS NAME appears in
      sanitized diagnostics, per the existing, unchanged
      `app/logging_config.py` contract);
    - lifecycle IDs, lifecycle rebuild counters, or any other internal
      lifecycle detail.

No lifecycle rebuild counters, lifecycle generation IDs, lifecycle
events, or other internal lifecycle information are exposed anywhere in
the UI - the returned `TradeSignalCorrectionResult`'s
`lifecycle_rebuild_performed`/`lifecycle_rebuild_result` fields are never
read by `app/streamlit_app.py`, which discards the method's return value
entirely.
