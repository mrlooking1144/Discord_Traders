# 4. Detailed Implementation Summary

`database/models.py` (additive only):

    - New frozen dataclass `AtomicChannelImportResult`, exactly four
      fields in this order: `channel`, `batch_result`, `lifecycle_result`,
      `operation`. Constructed inside the transaction after the operation
      row is created, but returned to the caller only after the
      surrounding transaction context exits and commits successfully. If
      commit or any earlier step fails, the call raises and no result
      reaches the caller - a failed or rolled-back attempt never produces
      one.

`database/service.py`:

    - New exception `ChannelExternalIdCollisionError(ValueError)` -
      raised in create mode when a candidate new channel external id
      already belongs to an existing channel for the resolved source.
    - `ingest_batch()` (Recovery Milestone R5) mechanically extracted:
      its former complete transaction body was moved, unchanged in
      logic, into a new private `_ingest_batch_no_commit()`; `ingest_batch()`
      itself becomes a thin wrapper that still validates its own inputs,
      still segments the raw text itself, still resolves source/channel
      via `get_or_create_source()`/`get_or_create_channel()`/
      `get_or_create_unspecified_channel()` exactly as before, then
      delegates the rest. `ingest_batch()`'s own public contract -
      every return value, count, the all-duplicate short-circuit, the
      narrow unique-constraint race carve-out, and its own transaction
      behavior - is completely unchanged; its full pre-existing
      regression suite in `tests/test_service.py` passed unmodified.
    - New private `_ingest_batch_no_commit(self, *, source, channel,
      raw_batch_text, reference_date, timezone, segmented_messages)`:
      never begins/commits/rolls back a transaction; never calls
      `segment_discord_batch()`, `get_or_create_source()`,
      `get_or_create_channel()`, `get_or_create_unspecified_channel()`,
      or any `rebuild_*` method. Reuses the existing
      `_duplicate_outcome()` and `_ingest_channel_message_no_commit()`
      helpers exactly as `ingest_batch()` already did - no second
      implementation of duplicate detection, the SAVEPOINT race
      carve-out, or extraction/signal creation exists anywhere.
    - New private `_collect_newly_stored_raw_message_ids(self,
      batch_result)`: collects every "stored" outcome's `raw_message_id`,
      raising a fixed `RuntimeError` if one is ever `None` ("Stored batch
      outcome is missing raw_message_id.") or if the collected count does
      not match `batch_result.stored_count` ("newly_stored_ids count does
      not match batch_result.stored_count.") - defensive validation for
      an invariant that should be structurally impossible given
      `MessageIngestOutcome`'s own contract, but is checked explicitly
      anyway; either failure still rolls back the entire surrounding
      transaction.
    - New public `import_channel_batch_with_lifecycle_rebuild()` - see
      Sections 5-9 below for its complete contract.

`tests/test_bulk_channel_import_service.py` (extended, not a new file -

# 5. Frozen Behavioral Contracts

    - `AtomicChannelImportResult` has exactly the four fields named
      above, in that exact order, with no defaults.
    - `ChannelExternalIdCollisionError` is a `ValueError` subclass,
      matching this module's existing structured-rejection convention
      (`TradeSignalNotFoundError`, `LifecycleUnsafeCorrectionError`).
    - The 15-message minimum is enforced ONLY by the new
      `import_channel_batch_with_lifecycle_rebuild()` - never by
      `ingest_batch()` or `_ingest_batch_no_commit()`, both of which
      still accept a batch smaller than 15 exactly as before.
    - `segmented_messages` is always the exact, already-segmented
      sequence the caller supplies (e.g. from a prior
      `app.discord_adapter.segment_discord_batch()` call) - the atomic
      method never calls `segment_discord_batch()` itself, proven by a
      dedicated mock-based test.
    - Create mode always calls `create_channel()` directly -
      `get_or_create_channel()` is never called anywhere in the atomic
      method.

# 6. Transaction and Rollback Guarantees

The entire operation - source/channel resolution (including channel
creation in create mode and source creation in create mode, when the
source did not already exist), `_ingest_batch_no_commit()`, the targeted
lifecycle rebuild, and `create_channel_import_operation()` - runs inside
exactly one existing `_r5_write_transaction()` (the same context manager
every other Recovery-track write method already uses; no new transaction
machinery was introduced).

Any exception raised anywhere in that sequence - a validation
`ValueError`, `ChannelExternalIdCollisionError`, an unconfirmed
`sqlite3.IntegrityError`, an ingestion failure, `LifecycleIntegrityError`/
`LifecycleSnapshotError` from the rebuild, the internal invariant
`RuntimeError`, or a failure while inserting the operation row itself -
rolls back every write made so far in that same call, including a newly
created `sources` row and a newly created `channels` row. A failed or
rolled-back attempt is never recorded as a `channel_import_operations`
row.

This is proven by four dedicated forced-failure tests
(`AtomicImportRollbackTests`) plus one in `AtomicImportCreateModeTests`
specifically targeting create-mode source rollback, each asserting a
complete ten-table dictionary (`sources`, `channels`, `traders`,
`import_batches`, `raw_messages`, `message_extractions`, `trade_signals`,
`trade_lifecycles`, `trade_lifecycle_events`, `channel_import_operations`)
is identical before and after the forced failure, via a new
`_atomic_write_counts()` test helper (added during the test-hardening
correction pass - see Section 15).

To be precise about where each guarantee applies:

    - A failure in the pure, pre-transaction validation (Section 7)
      performs zero writes and requires no rollback - `self.conn` is
      never touched, so there is nothing to undo.
    - Once `_r5_write_transaction()` begins, any exception raised
      anywhere inside it rolls back every write already made by the call
      up to that point.
    - Existing-mode source/channel validation (`get_source_by_name()`,
      then the channel existence/ownership/sentinel checks) happens
      inside the transaction, but strictly before any ingestion write -
      it is itself read-only, so a rejection there still leaves nothing
      to roll back even though `self.conn` is already inside the open
      transaction at that point.
    - Create-mode source creation (`get_or_create_source()`) can itself
      write a new `sources` row inside the transaction; that row is
      rolled back together with everything else if any later step in the
      same call fails.

# 7. Existing-Mode and Create-Mode Validation Rules

Pure, pre-transaction checks perform no database query or write and open
no transaction. `TradeService` already holds the caller-provided
connection (`self.conn`) from construction; these checks simply never use
it before raising:

    - `channel_mode` must be exactly `"existing"` or `"create"`.
    - `len(segmented_messages) >= 15`.
    - The shared `_validate_batch_inputs()` (source_name/reference_date/
      timezone/raw_batch_text shape).
    - Existing mode: `existing_channel_id` is required; must be a
      positive, non-boolean integer (bool explicitly rejected, since
      `isinstance(True, int)` is `True` in Python); `new_channel_external_id`
      and `new_channel_name` must both be `None` (rejected as
      contradictory arguments otherwise).
    - Create mode: `existing_channel_id` must be `None` (rejected as
      contradictory otherwise); `new_channel_external_id` is required and
      non-blank after stripping; the stripped value must not equal the
      reserved `UNSPECIFIED_CHANNEL_EXTERNAL_ID` sentinel;
      `new_channel_name` remains fully optional with `create_channel()`'s
      own existing behavior preserved exactly (no new nonblank-name
      rule).

Inside the transaction:

    - Existing mode: `source = get_source_by_name(...)` only - NEVER
      `get_or_create_source()`; a missing source is a fixed rejection
      (`"Source {source_name!r} does not exist."`) with no sources row
      ever created. The selected channel must exist
      (`"existing_channel_id {id} does not exist."`), must belong to the
      resolved source (`"channel {id} does not belong to source
      {source_name!r}."`), and must not be the reserved sentinel channel
      (`"existing_channel_id must not refer to the reserved unspecified
      channel."`).
    - Create mode: `source = get_or_create_source(...)` - MAY create a
      new `sources` row as part of the same atomic transaction (rolled
      back together with everything else on any later failure). An
      up-front `get_channel_by_external_id()` check raises
      `ChannelExternalIdCollisionError` if the id is already taken;
      otherwise `create_channel()` is called directly; a
      `sqlite3.IntegrityError` from that call is re-queried once - a
      confirmed real collision translates to
      `ChannelExternalIdCollisionError`, but an unconfirmed
      `IntegrityError` (the re-query also finds nothing) propagates
      completely unchanged, never mistranslated.

# 8. Duplicate-Only Behavior

When every element of `segmented_messages` is already present for the
resolved channel:

    - `_ingest_batch_no_commit()` takes its own existing "all duplicates"
      short-circuit: no `import_batches` row is created;
      `BatchIngestResult(import_batch_id=None, stored_count=0,
      duplicate_count=len(segmented_messages), ...)`.
    - No newly-stored raw-message ids exist, so the targeted-rebuild
      private helper `_rebuild_lifecycles_for_raw_message_ids_no_commit()`
      is never even called (proven by a dedicated mock assertion,
      `mock_rebuild.assert_not_called()`, added during the test-hardening
      pass) - `lifecycle_result` is instead the zero-valued result
      equivalent to `_RebuildCounters().to_result()`.
    - `create_channel_import_operation()` is still called, with
      `import_batch_id=None`, `stored_count=0`,
      `duplicate_count=batch_result.total_segmented` - satisfying the
      table's own CHECK constraint exactly, and recording a genuine
      success row that immediately becomes the channel's latest
      successful operation (`get_latest_channel_import_operation()`).

# 9. Targeted Lifecycle-Rebuild Behavior

Newly-stored raw-message ids (collected via the guarded
`_collect_newly_stored_raw_message_ids()`, Section 4) are passed to the
existing, unmodified private
`_rebuild_lifecycles_for_raw_message_ids_no_commit()` - the same targeted
rebuild engine `correct_trade_signal()` already uses internally. Only the
lifecycle keys touched by those specific raw messages are rebuilt; a
pre-existing, unrelated current lifecycle for a different
trader/symbol/channel is left completely untouched - proven by a
dedicated test that seeds an unrelated lifecycle first, then confirms its
id, `is_current` flag, and event count are byte-for-byte unchanged after
an unrelated atomic import.

No change was made to `database/lifecycle.py` or the lifecycle
repository layer.

# 15. Process Notes: Two Review Passes Before Commit

R9b went through the project's full Development workflow (design ->
review -> implement -> test -> review -> commit) with two distinct
correction passes on the plan/implementation before the commit above was
made:

    1. Architecture correction (applied to the plan, then implemented):
       source resolution now branches by `channel_mode` - existing mode
       never creates a source (uses `get_source_by_name()` only), create
       mode may (`get_or_create_source()`, with full rollback proof for
       the newly created row); strict rejection of contradictory
       mode-specific arguments was added; `existing_channel_id` is
       validated as a strict positive, non-boolean integer; the
       confirmed-race collision test design was corrected to be
       mock-driven rather than a real second-connection writer, since
       `_r5_write_transaction()`'s own `BEGIN IMMEDIATE` makes a genuine
       concurrent race unreachable under this connection's transaction
       convention.

       after initial implementation review): the exact-ordered-sequence
       proof replaced a set-only comparison; the ten-table
       `_atomic_write_counts()` helper was added and applied to every
       forced-failure/unconfirmed-error test, including explicit
       per-table assertions for the final-step
       (`test_operation_insert_failure_rolls_back_everything`) proof; the
       duplicate-only test now proves the targeted-rebuild helper is
       never called; a missing create-mode `None`-required-id test was
       added; three substring assertions were tightened to exact fixed
