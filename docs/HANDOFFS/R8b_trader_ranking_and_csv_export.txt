# 2. Purpose

R8a delivered the first user-facing view of R7's trader-performance
analytics, but deliberately deferred all ranking/comparison, a
minimum-sample-size threshold, and CSV export as lower-risk, separable
polish. R8b closes exactly that gap:

    - Trader ranking and comparison through the existing Trader Summary
      table - a user-selectable ranking metric and direction, default
      ranking by Average Return descending.
    - A minimum eligible-lifecycle threshold (default 3) that clearly
      marks, but never hides, a trader whose sample size is too small
      to rank confidently alongside qualifying traders.
    - Deterministic CSV export of both the ranked Trader Summary table
      and the currently filtered Lifecycle Drill-down table, generated
      entirely in Python via the standard library - never pandas.

R8b adds no schema change, no migration, no repository change, no
service change, no lifecycle-engine change, no model change, no parser
or adapter change, no new dependency, and performs no analytics
calculation of its own - like R8a, it is a pure consumer of the two
existing R7 read methods, plus new pure ranking/export helpers that
operate only on already-computed R7 data.

# 5. Exact Production Change

## 5a. `app/dashboard_formatting.py` (modified, still pure)

Retains R8a's guarantee: no `sqlite3` import, no import of
`database.repository`, `database.service`, or `database.analytics`, and
no `streamlit` import - confirmed by direct inspection during the
independent quality-review pass. New standard-library-only imports:
`csv`, `functools`, `io`, and `decimal.Decimal`.

New public constants:

    SORT_METRIC_CHOICES - the exact ten approved metrics, in order:
        "Average Return", "Median Return", "Win Rate", "Loss Rate",
        "Avg Winner Return", "Avg Loser Return", "Eligible Lifecycles",
        "Total Lifecycles", "Trader Name", "Trader ID"
    SORT_DIRECTION_CHOICES - ("Descending", "Ascending")
    SUMMARY_CSV_FIELDNAMES - the fixed, documented Trader Summary CSV
        column order (Trader Name, Trader ID, Meets Minimum Sample,
        then every remaining summary column in the same order as the
        on-screen table)
    LIFECYCLE_CSV_FIELDNAMES - the fixed Lifecycle Drill-down CSV column
        order, identical to the drill-down table's own column order

New/changed public functions:

    meets_minimum_sample(summary, min_eligible_lifecycles) -> bool
        summary["eligible_lifecycle_count"] >= min_eligible_lifecycles.
        Never recalculates eligible_lifecycle_count.

    format_minimum_sample(summary, min_eligible_lifecycles) -> str
        "Yes", or "No (n < threshold)" showing the real counts - never
        a bare "No" that hides them.

    build_summary_display_row(summary, *, min_eligible_lifecycles) -> dict
    build_summary_display_rows(summaries, *, min_eligible_lifecycles) -> list[dict]
        Signature changed (R8a's version took no threshold argument):
        now keyword-only `min_eligible_lifecycles`, required. Adds one
        new column, "Meets Minimum Sample", positioned immediately
        after "Trader". Every other column, and every existing
        formatting rule, is unchanged from R8a.

    rank_trader_summaries(summaries, *, sort_metric, descending,
                           min_eligible_lifecycles) -> list[dict]
        The new ranking function (plus private helpers
        `_sort_key_value()` and `_compare_ranked_summaries()`, and a
        module-private `_SORT_METRIC_FIELDS` vocabulary mapping each
        approved metric label to its raw field name and comparison
        type). Operates on the raw service dicts, never the
        display-formatted rows. Comparison rules: Decimal for every
        percentage/return field (never float, never a string/
        lexicographic compare), int for every count/trader_id field,
        case-insensitive string compare for trader_name. A `None`
        metric value always sorts last, in either direction. A trader
        below `min_eligible_lifecycles` always sorts after every
        qualifying trader; within each of those two tiers, the same
        metric/direction rule applies, and the final tie-break is
        always `trader_id` ascending, unconditionally of direction.
        Implemented via `sorted(summaries, key=functools.cmp_to_key(...))`
        - never mutates its input, always returns a new list. Raises
        `ValueError` for an unrecognized `sort_metric`.

    build_summary_csv_row(summary, *, min_eligible_lifecycles) -> dict
    build_summary_csv_rows(summaries, *, min_eligible_lifecycles) -> list[dict]
        Convert one/many already-ranked summary dicts into CSV-ready
        rows matching `SUMMARY_CSV_FIELDNAMES` exactly: the combined
        on-screen "Trader" label is split back into separate
        "Trader Name"/"Trader ID" columns (the one deliberate,
        approved divergence from the on-screen table); every other
        value is identical to `build_summary_display_row()`'s own
        formatting - the export is always what is on screen, never
        recalculated.

    build_lifecycle_csv_rows(results) -> list[dict]
        A direct delegation to the existing `build_lifecycle_display_rows()`
        - the drill-down CSV export is always byte-identical in content
        and order to the on-screen drill-down table. Never includes
        `analytics_error_detail` (that field is not, and has never
        been, part of the approved lifecycle display-row contract).

    rows_to_csv_string(rows, fieldnames) -> str
        Serializes display/CSV-ready rows into one deterministic CSV
        string using only `csv.DictWriter` + `io.StringIO` - never
        pandas. Always writes the header row, even for an empty `rows`
        list. Uses the `csv` module's default dialect: comma-delimited,
        `\r\n` line endings, standard quoting for commas/quotes/
        newlines. Repeated calls with the same input always produce
        byte-identical output.

# 8. Ranking, Minimum-Sample, and CSV Contract Rules

Ranking: see `rank_trader_summaries()` in Section 5a for the complete,
exact rule set (Decimal/int/case-insensitive-string comparison per
metric type, None-always-last in either direction, qualifying-before-
below-threshold tiering, trader_id-ascending final tie-break,
never-mutates-input). Ranking is always computed in plain Python before
any Streamlit rendering - never delegated to `st.dataframe`'s own
interactive column-sort, which remains available to the user for
on-screen inspection only and has no bearing on the CSV export or the
trader-selector order.

Minimum-sample threshold: a trader "qualifies" when
`eligible_lifecycle_count >= min_eligible_lifecycles` (the current
user-selected value, default 3). A below-threshold trader is never
hidden - no hide-below-threshold control exists anywhere in this
milestone - it remains fully visible in the table and CSV, tagged with
a clear "No (n < threshold)" indicator, and is always ranked after
every qualifying trader.

CSV contracts:

    Trader Summary CSV (`trader_performance_summary.csv`): current
    ranked order preserved; current threshold state reflected (both the
    "Meets Minimum Sample" column and tier position); "Trader Name" and
    "Trader ID" as separate columns; fixed column order per
    `SUMMARY_CSV_FIELDNAMES`; no analytics recalculation - every value
    is either passed through verbatim from the R7 service result or
    produced by the same formatting helpers the on-screen table uses.

    Lifecycle Drill-down CSV (`trader_lifecycle_drilldown_{trader_id}.csv`):
    exports only the currently selected trader's currently filtered
    (status/outcome/symbol) result set, in the exact order the
    drill-down table itself displays; uses the existing
    `build_lifecycle_display_row()` contract unchanged, so
    `analytics_error_detail` is never exported (that field has never
    been part of the drill-down table's column contract - the
    lifecycle-detail panel remains its one and only display surface).

    Serializer: Python standard-library `csv` + `io.StringIO` only, no
    pandas; deterministic `\r\n` line endings and standard CSV quoting;
    a repeated call with identical input always produces byte-identical
    output; an empty `rows` list produces a header-only string at the
    `rows_to_csv_string()` level.

# 12. Quality-Review History

An independent quality-review pass (separate from implementation)
inspected all five changed files against the approved R8b scope and
this handoff's own content, re-ran every required test command, and
reviewed test quality for tautological assertions, inadequate coverage,
false-positive patterns, brittle indexing, shared-fixture mutation, and
overstated test names. No BLOCKER and no MAJOR finding was raised, and
no finding indicated any production-behavior defect. Five MINOR
findings were identified and explicitly accepted by the Product Owner
without correction (all remain as originally implemented):

    1. Two `tests/test_app.py` AppTest-level tests
       (`test_summary_csv_exact_content`, `test_drilldown_csv_exact_content`)
       build their "expected" CSV by calling the same production
       ranking/CSV functions the app itself calls, then assert
       byte-equality against what the mocked `download_button` received
       - proving correct wiring, but not independently verifying content
       correctness (a shared bug would reproduce identically on both
       sides). No coverage gap in practice: content correctness is
       independently proven with literal values elsewhere (unit tests
       in `tests/test_dashboard_formatting.py`; real-database
       parsed-back literal-value tests in
       `tests/test_dashboard_integration.py`).
    2. `tests/test_dashboard_formatting.py::BuildLifecycleCsvRowsTests
       .test_identical_to_display_rows` is tautologically true by
       construction, since `build_lifecycle_csv_rows()` is a literal
       one-line delegation to `build_lifecycle_display_rows()`. No
       coverage gap: the delegated function's own correctness is
       thoroughly, independently tested with literal values elsewhere.
    3. `tests/test_dashboard_formatting.py::BuildSummaryCsvRowTests
       .test_remaining_fields_match_display_row_formatting` compares
       `build_summary_csv_row()`'s output against
       `build_summary_display_row()`'s own output for the same input,
       rather than a literal expected string. No coverage gap: the
       underlying formatting helpers are independently tested with
       literal values elsewhere.
    4. No single test combines "ascending direction" with "two
       non-`None` values within the below-threshold tier," nor combines
       a threshold change with a re-check of the trader-selector's
       option order or the summary CSV content in one flow - each half
       of each combination is proven separately. Low risk: the ranking
       comparator applies one shared, tier-agnostic code path for the
       metric/direction comparison, so the untested combinations
       exercise no code not already covered by the tested ones.
    5. Every ranking-control widget already carries an explicit `key=`,
       yet tests locate them by position (`at.selectbox[0..3]`,
       `at.number_input[0]`) rather than Streamlit `AppTest`'s
       supported `at.selectbox(key="...")` lookup, which would be
       immune to future widget-reordering. This is a pre-existing R8a
       convention, not introduced by R8b, though R8b's two new
       selectboxes required reindexing every existing positional
       reference.

Two additional OBSERVATIONs (non-actionable, no finding severity): no
