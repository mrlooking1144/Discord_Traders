# 6. R6.5a Objective

Integrate the existing controlled trade-signal correction workflow
(Milestone 2D.5's `TradeService.update_trade_signal()` controlled-
correction mode) with the R6 lifecycle system, so that a correction can
never leave lifecycle generations, membership events, signal pointers,
audit records, or immutable snapshots inconsistent with each other. The
entire operation - validation, the audit insert, the signal update, any
required lifecycle rebuild, and final membership-integrity validation -
had to become a single atomic, service-owned transaction.

# 7. Public API Added

New method on `database.service.TradeService`:

    TradeService.correct_trade_signal(
        trade_signal_id,
        expected_current_values,
        **changed_fields,
    ) -> TradeSignalCorrectionResult

This is a new, additional public method - it does not replace, wrap, or
change the signature of anything that existed before R6.5a.

# 8. Result Model Added

New immutable (`@dataclass(frozen=True)`) model in `database/models.py`:

    TradeSignalCorrectionResult
        trade_signal: TradeSignal
            The authoritative, corrected TradeSignal - reloaded from the
            database AFTER any lifecycle rebuild performed as part of
            the same correction, so trade_signal.lifecycle_id (when
            applicable) always reflects the post-rebuild pointer, never
            a stale pre-rebuild value.
        lifecycle_rebuild_performed: bool
            Whether a targeted lifecycle rebuild was performed as part
            of this correction.
        lifecycle_rebuild_result: LifecycleRebuildResult
            The existing R6.4 LifecycleRebuildResult model (reused, not
            duplicated) from the targeted rebuild, or a zero-valued
            LifecycleRebuildResult (never None) when
            lifecycle_rebuild_performed is False.

# 9. Exception Added

New exception in `database/service.py`:

    LifecycleUnsafeCorrectionError(ValueError)

Raised when a requested correction would change `action` on a
lifecycle-managed trade signal (`event_type IS NOT NULL`). Rejected
before any audit row, signal update, lifecycle mutation, or commit - the
entire correction is refused outright, never partially applied. A
ValueError subclass (matching this module's existing convention, e.g.
`TradeSignalNotFoundError`), so it can still be caught broadly as a
ValueError.

# 10. Approved Correction Fields

`correct_trade_signal()`'s `changed_fields` and `expected_current_values`
must each contain exactly these six fields - the same six approved by
Milestone 2D.5 for the legacy controlled-correction mode, unchanged by
R6.5a:

    symbol
    action
    option_type
    price
    expiration
    position_size

These are explicitly NOT part of the correction surface and are
rejected if supplied: `raw_message_id`, `trader_id`, `strike`,
`event_type`, `lifecycle_id`, any lifecycle metadata, any parser
metadata, any source identity. Strike correction was explicitly out of
scope for R6.5a.

# 11. Field-by-Field Lifecycle Behavior

- symbol / option_type / expiration (lifecycle-key fields): for a
  lifecycle-managed signal (`event_type IS NOT NULL`), an effective
  change to any of these triggers a targeted lifecycle rebuild. The
  lifecycle key itself
  (trader_id, symbol.upper(), option_type, strike, expiration) is
  unchanged - R6.5a never redefines lifecycle-key semantics.
- action: if the current signal is lifecycle-managed
  (`event_type IS NOT NULL`) and `action` would effectively change, the
  entire correction is rejected with `LifecycleUnsafeCorrectionError`
  (see section 9) - `event_type` is never reinterpreted or rewritten. If
  the current signal is legacy (`event_type IS NULL`), an action
  correction remains allowed under the existing controlled-correction
  rules. Supplying the same action value as already stored is treated
  as simply "not a changed field," not as an unsafe action change - it
  never trips `LifecycleUnsafeCorrectionError` by itself.
- price / position_size (non-key fields): corrections are allowed and
  never trigger a rebuild on their own, but still require stale-value
  protection, exactly one correction-audit record, atomic transaction
  handling, and the final lifecycle-membership integrity validation
  (run directly when no rebuild occurs).
- No-op: a correction whose six proposed values are identical to the
  six currently persisted values is rejected with a plain `ValueError`
  before any write - the existing Milestone 2D.5 no-op contract is
  reused unchanged.

# 12. Atomic Transaction Sequence

`correct_trade_signal()` performs pure, DB-free validation (field-name
shape checks and the shared `validate_trade_signal_update_fields()`
type/required-field validation) BEFORE opening any transaction. It then
opens exactly one transaction via the existing
`TradeService._r5_write_transaction()` context manager (the same R5/R6.4
transaction primitive - BEGIN IMMEDIATE, one COMMIT on success, full
rollback via `.rollback()` -> fallback SQL ROLLBACK -> connection close
on any failure) and, inside that single transaction:

    1. Fetch the authoritative current trade signal.
    2. Reject (TradeSignalNotFoundError) if it does not exist.
    3. Build the canonical current six-field snapshot.
    4. Compare it to expected_current_values; reject
       (StaleTradeSignalError) on any mismatch.
    5. Reject (ValueError) if changed_fields is identical to the
       current snapshot (a no-op).
    6. Classify which of the six fields actually differ.
    7. If `action` differs and event_type IS NOT NULL, reject
       (LifecycleUnsafeCorrectionError) - nothing has been written yet.
    8. Write exactly one trade_signal_edits audit row (pre-correction
       values, via the existing create_trade_signal_edit()).
    9. Apply the update via the existing repository primitive
       (update_trade_signal()).
    10. Decide whether a targeted lifecycle rebuild is required (see
        section 13).
    11a. If required: invoke the existing PRIVATE no-commit rebuild
         helper, TradeService._rebuild_lifecycles_for_raw_message_ids_
         no_commit([raw_message_id]) - this already performs its own
         final lifecycle-membership integrity validation internally and
         raises LifecycleIntegrityError/LifecycleSnapshotError on
         failure.
    11b. If not required: call
         database.repository.validate_lifecycle_membership_integrity()
         directly and raise LifecycleIntegrityError if it reports any
         violation.
    12. Reload the authoritative trade signal (post-rebuild, if any).
    13. Return a TradeSignalCorrectionResult.

On normal completion, _r5_write_transaction() commits exactly once. Any
exception anywhere in steps 1-13 rolls back the entire transaction -
the audit row, the signal update, and any lifecycle writes are all
undone together; there is no partial-success state.

IMPORTANT: correct_trade_signal() never calls the PUBLIC
rebuild_lifecycles_for_raw_message_ids() - that method opens its own
_r5_write_transaction() and would raise RuntimeError (or worse, nest
incorrectly) if called from inside an already-open transaction. It calls
only the private _no_commit variant, which never begins, commits, or
rolls back a transaction of its own.

# 13. Lifecycle Rebuild Decision Rules

A targeted rebuild (via the corrected signal's own raw_message_id) is
performed when EITHER:

  (a) The signal is lifecycle-managed (event_type IS NOT NULL) AND an
      effective change occurred to symbol, option_type, or expiration.

  (b) The signal is legacy (event_type IS NULL) AND it unexpectedly
      carries stale lifecycle state - a non-NULL trade_signals.
      lifecycle_id pointer, and/or existing current lifecycle-event
      lineage referencing its raw_message_id (discovered via the
      existing get_current_lifecycle_ids_for_raw_message_ids()). This
      should never arise through the approved API surface (ingestion
      never sets event_type on a legacy signal; the lifecycle engine
      never links an ineligible signal), but if found, R6.5a
      self-heals it via the same targeted rebuild path regardless of
      which of the six fields was actually being corrected.

Otherwise, no rebuild is performed - the final membership-integrity
validation still runs directly (step 11b above) before commit. Every
affected lifecycle key is rebuilt at most once per correction; unrelated
lifecycle keys/signals are never touched. No broad
(rebuild_all_lifecycles()-style) rebuild is ever triggered by a
correction.

# 14. Complete/Incomplete Contract Handling

Lifecycle-key completeness is exactly the existing R6 engine's rule,
unchanged by R6.5a: option_type/strike/expiration must be either all
None (equity identity) or all present (complete option identity); any
other combination is an incomplete contract identity, handled by the
existing incomplete-singleton machinery (an unresolved singleton
generation, status "unresolved", remaining_fraction "0", ambiguity flag
"incomplete_contract_identity").

Because strike is not part of the approved correction surface (section
10), R6.5a can only move a signal between complete and incomplete via
option_type/expiration:

  - Incomplete -> complete: the stored signal already has a strike, and
    the correction supplies the missing option_type and/or expiration.
    Handled by the same targeted rebuild that discovers the old
    (incomplete-singleton) key from lineage and the new (complete) key
    from the corrected signal - the old singleton is superseded and a
    normal keyed lifecycle generation is created.
  - Complete -> incomplete: option_type or expiration is cleared while
    strike remains present. The old complete-key generation is
    superseded and a fresh incomplete-identity singleton is created for
    the corrected signal.
  - Equity -> complete option identity is impossible in R6.5a, since
    strike cannot be introduced via correction.
  - A partially populated option identity is always handled by the
    existing incomplete-singleton behavior - R6.5a introduces no new
    completeness rule of any kind; it only decides WHEN to invoke the
    existing rebuild that already implements this.

# 15. Rollback Guarantees

Any exception raised at any point in the sequence in section 12 - a
pure-engine failure inside build_lifecycle_sequence(), a repository/
SQLite failure during persist_lifecycle_builds(), a
LifecycleIntegrityError from either the internal rebuild-path validation
or the direct no-rebuild-path validation, or a LifecycleSnapshotError
from decoding a corrupted historical snapshot mid-rebuild - rolls back
the ENTIRE transaction: the trade_signal_edits audit row, the
trade_signals column update, every trade_lifecycles supersession/
creation, every trade_lifecycle_events insert, and every
trade_signals.lifecycle_id pointer change made during that call are all
undone together. This was proven with real SQLite writes (not mocks of
the transaction machinery itself) in every rollback test - see section
16.

Per the reviewed design, R6.5b:

  - Migrates app/streamlit_app.py's existing "Correct Signal" workflow
    from TradeService.update_trade_signal()'s controlled-correction
    mode to the new TradeService.correct_trade_signal().
  - Removes the caller-side correction commit and rollback handling that
    the old (caller-owned-transaction) pattern currently requires in
    the UI, since correct_trade_signal() now owns its own transaction.
  - Preserves every existing approved user-visible correction message
    exactly, unchanged (see Milestone 2D.5's fixed message set in
    docs/PROJECT_STATUS.md).
  - Preserves the correction form state after EVERY rejected save -
    never clearing it in any of these cases:
      * a validation failure;
      * a no-op correction;
      * a lifecycle-unsafe action correction
        (LifecycleUnsafeCorrectionError);
      * a stale-value conflict (StaleTradeSignalError);
      * a signal-not-found conflict (TradeSignalNotFoundError);
      * a lifecycle-integrity failure (LifecycleIntegrityError);
      * a snapshot failure (LifecycleSnapshotError);
      * a database failure (e.g. sqlite3.Error);
      * any other unexpected failure.
    In every one of these cases the form stays open with the user's
    input intact.
  - Clears correction form state ONLY after: a successful save; an
    explicit Cancel; a change of the selected signal; or a filter
    change that removes the signal from view. No other event may clear
    the form.
  - Adds new UI and integration test coverage for the migrated
    workflow.
  - Stops before Recovery Milestone R6.6 (real-corpus acceptance).

This handoff intentionally does NOT re-derive or re-design R6.5b from
scratch - the design already exists and was already reviewed. The
remaining gate before implementation is verification of that reviewed
design against the current committed repository, followed by explicit
Product Owner approval to begin implementation.
