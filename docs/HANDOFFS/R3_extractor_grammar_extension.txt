# Summary

Objective: add a second, independent parsing entry point to
`app/parser.py` - `extract_trade_event()` - that converts one Discord
alert's already-segmented `cleaned_text` (as produced by Recovery
Milestone R2's `app/discord_adapter.segment_discord_batch()`) into a
single structured trade-event dict, classified into an approved trade
lifecycle event type. This targets a different input shape than the
existing `parse_message()` (one signal per independent line): one alert
that may span several lines - an action line, a duplicated bare
contract-restatement line, a bare fraction/"ALL OUT" confirmation line,
a "$OLD -> $NEW (+NN%)" stated-return line, and free-text commentary.

`extract_trade_event()` is fully source-agnostic: it never imports
`app.discord_adapter` and is a pure function of the text it is given,
consistent with this module's existing source-independence guarantee.
It is versioned independently via the new `PARSER_VERSION = "v2"`
module constant.

# Grammar and Semantics

## Supported action verbs

`extract_trade_event()` recognizes exactly these eight verbs
(case-insensitive on input, preserved uppercase on output, never
aliased to one another - e.g. `BUY` is never rewritten to `BTO`):

    BOUGHT, SOLD, BTO, STC, BTC, STO, BUY, SELL

## Opening vs. closing role

Classification is by opening/closing role, not by surface "buy/sell"
wording:

- Opening actions (open a position): BTO, BUY, BOUGHT, STO
  (STO opens a short position; the other three open a long position)
- Closing actions (close a position): STC, SELL, SOLD, BTC
  (BTC closes a short position; the other three close a long position)

## Approved event types

Exactly five event types are ever produced - no other event type exists
and none may be invented without separate approval:

    ENTRY, ADD, ROLL_UP, PARTIAL_EXIT, FULL_EXIT

Classification rules for a non-contradictory alert:

- Opening action + `[ADD]` annotation -> ADD
- Opening action + `[ROLL UP]` annotation -> ROLL_UP
- Opening action, no conflicting closing qualifier -> ENTRY
- Closing action + `ALL OUT` qualifier -> FULL_EXIT
- Closing action + a required fraction (1/2, 1/3, 1/4, 1/6, 1/8, 1/16)
  -> PARTIAL_EXIT

A stop-out (e.g. "HIT STOP") is a FULL_EXIT whose reason is preserved
verbatim in the `notes` field - it is never treated as a separate event
type such as a hypothetical "STOP_EXIT".

## STO / BTC semantic correction

An initial implementation placed STO in the same bucket as
SOLD/STC/SELL/BTC for event-type purposes, which would have
misclassified "STO ... ALL OUT" or "STO ... 1/2" as an exit - silently
reporting a brand-new short position as though it were being closed.
This was identified and corrected before commit:

- STO now classifies via the same annotation-based *opening* rule as
  BTO/BUY/BOUGHT (there is no approved separate short-entry event type,
  so a short entry is represented the same way a long entry is).
- BTC continues to classify via the same qualifier-based *closing* rule
  as STC/SELL/SOLD, since BTC closes a short position - a closing/exit
  event, regardless of its "buy" wording.

## action_qualifier_conflict - contradictory opening + closing qualifier

A further, narrower defect was then identified and corrected: an
opening action combined with a closing-only qualifier (`ALL OUT` or a
fraction) is semantically contradictory - e.g. "STO ... ALL OUT" cannot
be an entry, since there is nothing open yet to be "all out" of - and
no approved event type represents it. This is never guessed into
ENTRY, ADD, ROLL_UP, PARTIAL_EXIT, or FULL_EXIT.

Resolution:
- `event_type` is `None` for any opening action (BTO/BUY/BOUGHT/STO)
  combined with a closing-only qualifier found on the action line
  itself (`ALL OUT` or a required fraction), whether or not a bracket
  annotation is also present.
- A new ambiguity flag, `FLAG_ACTION_QUALIFIER_CONFLICT`
  (`"action_qualifier_conflict"`), is appended to `ambiguity_flags` so
  the alert is preserved for manual review rather than silently
  misclassified. No existing flag represented this condition
  (`FLAG_QUALIFIER_MISSING` means *absence*, not *conflict*).
- This is not treated as a parse failure: `action`, `symbol`, `price`,
  `strike`, `option_type`, the raw qualifier, `notes`, and every other
  extracted field are retained unchanged, and `parse_status` still
  reaches `PARSE_STATUS_PARSED` when action/symbol/price were all
  found - only `event_type` is withheld.
- This rule applies uniformly to every opening verb, not only STO -
  BTO/BUY/BOUGHT combined with `ALL OUT` or a fraction is equally
  contradictory and produces the same `event_type=None` +
  `FLAG_ACTION_QUALIFIER_CONFLICT` result.

Internally, `_parse_action_line()` now tracks the raw closing qualifier
(`close_qualifier`) independently of the merged, display-facing
`qualifier` field, so a conflict is detectable even when an annotation
is also present on the same line. This is a private-helper-only change;
the public `extract_trade_event()` result schema
(`_EXTRACTOR_RESULT_KEYS`) is unchanged.

## Known non-blocking boundary

The `action_qualifier_conflict` detection only inspects the action line
itself. A hypothetical alert where a contradictory `ALL OUT`/fraction
qualifier arrived on a *separate* line (rather than the action line)
would not be caught by this rule, since
`_is_bare_qualifier_confirmation_line()` treats such follow-up lines as
duplicate confirmations to discard, not as classification input. No
such shape exists anywhere in the current 68-message corpus or in the
authorized R3 grammar, so this is recorded as a known boundary for
future review, not a defect blocking R3.
