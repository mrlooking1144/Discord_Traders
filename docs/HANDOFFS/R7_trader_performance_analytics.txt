# 2. Purpose

R6.7 exposed persisted lifecycle-event evidence through a validated,
decoded read API, but no method anywhere above the repository layer
could compute a return, classify a win/loss outcome, or summarize one
trader's performance across every current lifecycle. The Product Owner's
target workflow - pasting Discord messages into the application and
viewing performance by trader - still had no analytics layer to draw on.

R7 closes exactly that gap:

    - A pure, database-independent analytics engine
      (`database/analytics.py`) that computes one lifecycle generation's
      price-return outcome, and reduces many such results into one
      trader's performance summary.
    - One new unbounded (no `LIMIT`) repository reader
      (`database.repository.get_all_current_trade_lifecycles()`) so an
      analytics-completeness query can never silently truncate.
    - Three new public, read-only `TradeService` methods that fetch,
      validate/decode, and translate the pure engine's results into
      plain dicts at the service boundary - one strict (raises on bad
      evidence) and two tolerant (never abort on one bad lifecycle).

R7 adds no schema change, no migration, no lifecycle-engine change, no
model change, and no UI. It is the analytics layer only; R8 (the
trader-performance dashboard/UI) remains separate, unstarted, future
work.

# 5. Exact Production Change

## 5a. `database/repository.py` (additive only)

New function:

    get_all_current_trade_lifecycles(
        conn: sqlite3.Connection,
        *,
        trader_id: int | None = None,
    ) -> list[TradeLifecycle]

An unbounded (no `LIMIT` of any kind) reader of every current
(`is_current = 1`) lifecycle generation, optionally scoped to one
`trader_id`. Deliberately distinct from the pre-existing
`list_current_trade_lifecycles()`, which is a bounded (default `LIMIT
100`), newest-first *display* reader for the Review UI and offers no way
for a caller to detect truncation - it must never be repurposed to back
an analytics-completeness guarantee. This new function instead follows
the same unbounded-scan precedent already established by
`get_all_current_lifecycle_keys()` (used by `rebuild_all_lifecycles()`
for whole-database correctness), returning full `TradeLifecycle` rows
ordered by `id` ascending (deterministic, not a "newest first"
convention).

## 5b. `database/analytics.py` (new, pure module)

Contains no database access whatsoever - no `sqlite3` import, no import
of `database.repository` or `database.service` - mirroring
`database/lifecycle.py`'s proven pure-module precedent. Every function
takes already-fetched, already-validated data and returns deterministic,
database-independent results. Scope boundary (approved R7 planning
review): price-return analytics only - no dollar P&L, no contract
multipliers, no position quantity, since none of that evidence exists
anywhere in the committed schema; `trade_signals.stated_return_pct` is
never read for any calculation (audit-only field).

Public surface:

    ExitLeg (frozen dataclass) - one exit event's contribution
        (trade_lifecycle_event_id, trade_signal_id, sequence_index,
        event_type, consumed_fraction as an exact fractions.Fraction
        string, exit_price).

    LifecycleAnalyticsResult (frozen dataclass) - one lifecycle
        generation's complete result: identity/status fields,
        outcome/direction, entry/exit prices, exit_legs,
        gross_price_return_pct, eligibility flags, ambiguity/exclusion
        reasons, and source_event_ids. Every Decimal-valued field is a
        plain string, never a float.

    build_data_error_result(...) -> LifecycleAnalyticsResult
        Builds a 'data_error' result for a lifecycle whose evidence is
        structurally broken (zero membership events, or a
        signal_snapshot that failed validation/decoding). No return or
        outcome metric is ever computed or fabricated; source_event_ids
        reflects whatever event ids were actually found, never assumed
        empty.

    compute_lifecycle_analytics(...) -> LifecycleAnalyticsResult
        Computes one lifecycle's complete result from already-decoded,
        already-ordered member events plus already-resolved
        opened_at/closed_at timestamps. Never raises for any input shape
        it can receive under its documented precondition (events
        non-empty and pre-validated).

    summarize_trader_performance(...) -> TraderPerformanceSummary
        Reduces a list of LifecycleAnalyticsResults for one trader into
        one summary - status-partition counts, eligible/not-scored/
        data-error counts, win/loss/breakeven counts and rates, average
        and median gross_price_return_pct, average winner/loser return,
        sorted id lists per category, and an exclusion-reason frequency
        count. No snapshot is read or decoded again; every rate/average
        is None (never 0) when its denominator is zero.

## 5c. `database/service.py` (additive only)

Two new exceptions:

    TradeLifecycleNotFoundError(ValueError) - raised by
        get_trade_lifecycle_analytics() when trade_lifecycle_id
        references no trade_lifecycles row at all, current or
        superseded. Matches this project's existing not-found
        convention (TradeSignalNotFoundError).

    LifecycleAnalyticsError(Exception) - raised by
        get_trade_lifecycle_analytics() when a trade_lifecycles row
        exists but has zero trade_lifecycle_events membership rows.
        Distinct from LifecycleSnapshotError (malformed snapshot
        content); never raised by the tolerant read paths, which
        instead surface this same condition as a per-lifecycle
        'data_error' result.

Three new public, read-only `TradeService` methods (no write, no
transaction, no commit/rollback in any of the three - the same
caller-owned-connection convention as R6.7's
`list_trade_lifecycle_events()`):

    get_trade_lifecycle_analytics(self, trade_lifecycle_id: int) -> dict
        Strict. Accepts any id, current or superseded. Fetches the
        lifecycle and its membership, decodes every snapshot via the
        existing, unmodified `_validate_and_decode_snapshot()`, resolves
        opened_at/closed_at from the immutable raw_messages evidence
        behind the opener/closer signal, and returns the complete
        LifecycleAnalyticsResult as a plain dict. Raises
        TradeLifecycleNotFoundError, LifecycleAnalyticsError, or a
        propagated-unchanged LifecycleSnapshotError - never a silently
        substituted result.

    list_current_trade_lifecycle_analytics(self, *, trader_id=None)
        -> list[dict]
        Tolerant per lifecycle, no truncating limit. Built on
        get_all_current_trade_lifecycles() (Section 5a), so it can never
        silently omit a current lifecycle. A malformed snapshot or a
        zero-event lifecycle never aborts the call - it produces an
        explicit 'data_error' result in its place instead. Ordered by
        trade_lifecycle_id ascending.

    list_trader_performance_summaries(self, *, trader_id=None)
        -> list[dict]
        One summary per trader, aggregated strictly from current-
        lifecycle analytics results. Shares its underlying per-lifecycle
        computation with list_current_trade_lifecycle_analytics() via
        the same private _lifecycle_analytics_or_error() helper, so no
        signal_snapshot is ever decoded twice and the two public methods
        can never disagree about one lifecycle's own result. Never ranks
        or sorts by any performance metric - trader_id ascending only,
        leaving any ranking/comparison-display decision to R8. Ordered
        by trader_id ascending.

Supporting private helpers added to `database/service.py`:
`_resolve_event_timestamp()` (resolves a member signal's canonical UTC
timestamp by reading `get_raw_message_by_id()` live, since
`raw_messages.received_at` is never updated once written),
`_build_lifecycle_analytics()`, `_lifecycle_analytics_or_error()` (the
tolerant wrapper), `_lifecycle_analytics_result_to_dict()`, and
`_trader_performance_summary_to_dict()` (both dict-conversion helpers
convert every tuple-typed field to a list for the public, JSON-friendly
boundary, matching R6.7's plain-dict convention).

# 6. Trade-Direction, Fraction-Weighting, and Exclusion Rules

Trade-direction evidence (approved R7 planning review): `app/parser.py`
classifies `BTO`/`BUY`/`BOUGHT` and `STO` identically as *opening*
actions (`STO` opens a short - there is no separate short-entry
`event_type`), and `STC`/`SELL`/`SOLD`/`BTC` identically as *closing*
actions. `event_type` alone cannot distinguish a long position from a
short one; only the opener's own raw `action` text can.
`_resolve_direction()` classifies `BTO`/`BUY`/`BOUGHT` as `"long"`,
`STO` as `"short"`, and anything else as `None` (never guessed). The
real 68-message corpus (R6.6) contains no `STO`/`BTC` occurrences, but
the grammar supports them, so a short direction is detected, never
assumed absent, and is classified `not_scored`
(`short_direction_not_scored`) - never scored under the long-position
return formula.

Fraction-weighted partial exits: `_build_exit_legs()` replays a
generation's ordered member events and reconstructs its exit history
using `fractions.Fraction` (never Decimal) for `consumed_fraction`,
since several approved qualifier tokens (`1/3`, `1/6`) are
non-terminating in base 10. Each approved token (`1/2`, `1/3`, `1/4`,
`1/6`, `1/8`, `1/16`) consumes that exact fraction of the *original*
position; a `FULL_EXIT` always consumes whatever fraction remains. The
final `gross_price_return_pct` is the fraction-weighted sum of each
exit leg's own return, never the naive "entry price to final exit price
only" shortcut - proven by a dedicated test
(`test_two_partial_exits_then_final_full_exit_is_fraction_weighted`)
asserting the correct 75% result is produced and explicitly is not
100%.

Scale-in exclusion: an `ADD` event sets `has_add = True`; any lifecycle
with an `ADD` is excluded from return/outcome metrics
(`scale_in_cost_basis_not_modeled`) because this schema has no cost-basis
model for a scaled-in position, while still counting normally toward
status-count aggregates (`eligible_for_status_counts` stays `True`).

Short-position exclusion: as above, `short_direction_not_scored`.

Other not-scored/data-error conditions, each producing its own named
exclusion reason and never a fabricated value: non-`closed` status
(`status_<status>`), no verified opener (`no_verified_opener`),
unparseable or missing entry price (`unparseable_entry_price` /
`missing_entry_price`), zero entry price (`entry_price_zero`), a missing
exit price on any leg or on a closed lifecycle with no exit legs at all
(`missing_exit_price`), and an unresolvable exit fraction
(`unresolvable_exit_fraction` - a defensive-only branch, since the pure
lifecycle-matching engine already routes any genuinely unresolvable
fraction to its own standalone `unresolved` singleton before it can ever
reach a real generation's membership).

# 7. Strict vs. Tolerant Analytics APIs

Strict: `get_trade_lifecycle_analytics()` - a caller asking about one
specific, named lifecycle id receives the unfiltered truth or an
exception (`TradeLifecycleNotFoundError`, `LifecycleAnalyticsError`, or
`LifecycleSnapshotError`), never a silently substituted 'data_error'
placeholder.

Tolerant: `list_current_trade_lifecycle_analytics()` and
`list_trader_performance_summaries()` - one corrupted lifecycle
(zero-event membership, or a malformed/contradictory signal_snapshot)
can never abort an entire list or summary call. The failure is never
hidden: it is preserved verbatim in the affected result's
`analytics_error_detail` and counted in `snapshot_error_count` /
`snapshot_error_lifecycle_ids` by the trader summary.

# 8. No-Truncation Lifecycle Retrieval

Both tolerant methods are built on
`get_all_current_trade_lifecycles()` (Section 5a), which has no `LIMIT`
of any kind - proven directly by
`test_no_truncation_over_one_hundred_current_lifecycles` (service layer)
and `test_more_than_one_hundred_current_lifecycles_are_not_truncated`
(repository layer), each inserting 101 current lifecycles - one more
than the pre-existing, deliberately bounded
`list_current_trade_lifecycles()`'s own default `LIMIT 100` - and
asserting all 101 are returned with no truncation and no double-count.

# 9. Decimal Precision and Rounding Rules

All calculation happens inside a `decimal.localcontext()` with
`prec = 50` (`_CALC_PRECISION`) and `ROUND_HALF_EVEN`, so an
intermediate repeating-fraction division (e.g. a `1/3` partial exit)
never loses precision mid-calculation. Every public percentage field
(`gross_price_return_pct`, `weighted_average_exit_price`, and every rate
or average in `TraderPerformanceSummary`) is quantized to exactly six
decimal places (`Decimal("0.000001")`, `ROUND_HALF_EVEN`) only at the
point of public serialization, via `_quantize_pct()` - classification
decisions (win/loss/breakeven, entry-price-zero) always compare the
unquantized, full-precision value first, never the rounded display
value. Every Decimal-valued result field is a plain string, never a
Python `float`, matching this project's existing price/strike
serialization convention - proven by
`test_no_float_anywhere_in_result_fields` and
`test_repeating_fraction_rounds_deterministically_to_six_places`. Median
uses true division for an even-count dataset
(`test_median_even_count_uses_true_division_not_floor`), never floor
division.

# 13. Architecture Notes

    - `database/analytics.py` is a pure module with the same
      no-database-access guarantee as `database/lifecycle.py` - both
      are independently unit-testable with zero SQLite involvement.
    - `TradeService` remains the sole owner of fetch/decode/validate
      orchestration; the pure analytics engine never sees a raw
      `sqlite3.Connection`, a `TradeLifecycleEvent`, or undecoded JSON.
    - The unbounded `get_all_current_trade_lifecycles()` and the
      pre-existing, bounded `list_current_trade_lifecycles()` now
      coexist deliberately: the former backs analytics-completeness
      guarantees, the latter continues to back the Review UI's own
      bounded display - neither was repurposed to serve the other's
      contract.
    - The architecture remains modular and provider-independent: R7
      touches only a new pure module and the service layer's read
      surface for lifecycles already persisted through the existing,
      source-independent `trade_lifecycles`/`trade_lifecycle_events`
      tables.
