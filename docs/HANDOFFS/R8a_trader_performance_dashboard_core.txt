# 2. Purpose

R7 computed trader-performance analytics but exposed them only through
`TradeService` methods - no UI existed anywhere for the Product Owner
to actually see a trader's performance. R8 (the dashboard/UI milestone)
was scoped, then split into two approved sub-milestones:

    - R8a (this milestone): the core dashboard - a third sidebar
      workflow showing a trader summary table and a per-trader,
      filterable drill-down with full lifecycle and exit-leg evidence.
      This alone satisfies the Product Owner's original target
      workflow of viewing performance by trader inside the application.
    - R8b (separate, unstarted, requires its own approval): ranking/
      sort-metric selection and CSV export - polish deferred from R8a
      as lower-risk, separable work.

R8a adds no schema change, no migration, no repository change, no
service change, no lifecycle-engine change, no model change, no parser
or adapter change, no new dependency, and performs no analytics
calculation of its own - it is a pure consumer of the two existing R7
read methods.

# 5. Exact Production Change

## 5a. `app/streamlit_app.py` (modified)

The sidebar's `st.sidebar.radio("Workflow", [...])` options list gains
a third entry, `"Trader Performance"` - the one approved change to
that line. A new `elif workflow == "Trader Performance":` branch is
appended after the existing Review Signals branch. Manual Message
Entry, Review Signals, and Correct Signal code is otherwise completely
unchanged - not "byte-for-byte unchanged" (the options list line itself
necessarily changed), but behaviorally unchanged and fully
regression-tested (the complete pre-existing `tests/test_app.py` suite,
minus one disclosed test-expectation update to the options list,
passes unmodified).

The new branch:

    - Reads `db_path = resolve_database_path()`. If
      `not Path(db_path).exists()`, shows the fixed
      `_DASHBOARD_EMPTY_MESSAGE` and does nothing else - never calls
      `initialize_database()`, never opens a connection, never creates
      a file or directory. Identical guarantee to Review Signals.
    - Otherwise opens one connection (`conn: sqlite3.Connection | None
      = None` declared before the `try`), constructs one
      `TradeService`, and calls
      `service.list_trader_performance_summaries()`. A `finally:
      if conn is not None: conn.close()` at the very end of the branch
      closes the connection on every path - success, an exception
      during the summary fetch, or an exception anywhere inside the
      nested rendering code - exactly mirroring Review Signals'
      established shape.
    - An exception fetching summaries is caught, logged via the
      existing sanitized `log_operation_failure()`, and shown as the
      fixed `_DASHBOARD_LOAD_FAILURE_MESSAGE` - never raw exception
      text.
    - An empty summary list shows `_DASHBOARD_EMPTY_MESSAGE` (the same
      fixed message reused for both the missing-database and
      empty-database cases, matching the Review Signals precedent).
    - Otherwise renders the Trader Summary table via
      `build_summary_display_rows(summaries)` (see Section 5b), then a
      trader selectbox (`key="dashboard_trader_select"`, options are
      the summaries' own `trader_id` values in their own returned
      order, `format_func` uses `build_trader_label()`). Before
      rendering, if the previously selected trader_id is no longer
      present, `st.session_state.pop("dashboard_trader_select", None)`
      is called first - the same pattern already used for
      `correction_signal_id` in Review Signals - so Streamlit falls
      back to a valid default instead of raising
      `StreamlitAPIException` for a stale value.
    - Calls `service.list_current_trade_lifecycle_analytics(trader_id=
      selected_trader_id)` in its own nested `try`/`except`; a failure
      is logged and shown as the fixed
      `_DASHBOARD_DRILLDOWN_LOAD_FAILURE_MESSAGE`.
    - Renders a status `st.multiselect`, an outcome `st.multiselect`,
      and a symbol `st.text_input` (all independently optional; an
      empty multiselect selection or blank text input means "no filter
      on that dimension"), applies `filter_lifecycle_results()` (see
      Section 5b), and either shows
      `_DASHBOARD_NO_MATCHING_LIFECYCLES_MESSAGE` (if the filtered list
      is empty) or renders the drill-down table via
      `build_lifecycle_display_rows(filtered_results)`.
    - Renders a second selectbox (`key="dashboard_lifecycle_select"`,
      options are the filtered results' own `trade_lifecycle_id`
      values) with the same stale-value pop-before-render guard - one
      inclusion check against the current, filtered `lifecycle_ids`
      handles both "the trader changed" and "a filter narrowed the
      lifecycle out" without distinguishing the two causes.
    - Builds `build_lifecycle_detail(selected_result)` (see Section 5b)
      and renders "Data Error Detail: {error_detail}" (the em-dash
      placeholder for a non-error lifecycle, or the verbatim
      `analytics_error_detail` string for a `data_error` one - the
      *only* place that field is ever rendered), then either "No exit
      events for this lifecycle." (an empty `exit_legs`) or the
      exit-leg table.

## 5b. `app/dashboard_formatting.py` (new, pure module)

Contains no database access and no Streamlit dependency whatsoever - no
`sqlite3`, `database.repository`, `database.service`, `database.
analytics`, or `streamlit` import anywhere in the file, confirmed by
direct inspection during the independent quality-review pass, not just
by the absence of an import error. Every function takes an
already-fetched plain dict or list of dicts - the exact shape
`TradeService.list_trader_performance_summaries()`/
`list_current_trade_lifecycle_analytics()` already return - and returns
a display-ready value or row dict. No function computes, re-derives,
rounds, or ranks any R7 analytics value.

Public surface (eleven functions):

    format_optional_value(value) -> str
        str(value), or the fixed em-dash placeholder ("—") if
        value is None.

    format_percent(value: str | None) -> str
        f"{value}%" for an already-quantized R7 percentage string, or
        the em-dash placeholder if value is None (a zero-denominator
        rate/average per R7's own contract - never rendered as "0%").
        Never parses value as a number.

    format_data_error_count(count: int) -> str
        "0" when count == 0, else a visible "⚠ {count}" indicator
        - the summary table's only exposure of a data-error condition,
        never the verbatim analytics_error_detail text.

    build_trader_label(trader_id, trader_name) -> str
        "{trader_name} (ID {trader_id})" - used everywhere a trader is
        displayed or selected, so two identically-named traders are
        never confused.

    build_summary_display_row(summary) -> dict
    build_summary_display_rows(summaries) -> list[dict]
        Convert one/many list_trader_performance_summaries() dicts into
        display-ready summary-table row(s), order preserved exactly (no
        ranking applied by R8a).

    filter_lifecycle_results(results, *, statuses=None, outcomes=None,
                              symbol=None) -> list[dict]
        Pure, order-preserving filter over an already-fetched
        list_current_trade_lifecycle_analytics() result list. An empty
        or None statuses/outcomes list means "no filter on that
        dimension" (never "match nothing"). symbol is stripped and
        uppercased; blank (including whitespace-only) means no filter;
        a non-blank value requires an exact match (never substring).
        Never mutates results.

    build_lifecycle_display_row(result) -> dict
    build_lifecycle_display_rows(results) -> list[dict]
        Convert one/many lifecycle analytics dicts into display-ready
        drill-down row(s), including a short "Data Error" indicator
        (never the verbatim analytics_error_detail text).

    build_exit_leg_display_rows(exit_legs) -> list[dict]
        Convert one lifecycle's exit_legs list into display rows: Event
        Type, Consumed Fraction, Exit Price, Sequence Index - in the
        order already provided (sequence_index ascending, as R7
        guarantees). Returns [] unchanged if exit_legs is empty.

    build_lifecycle_detail(result) -> dict
        {"error_detail": str, "exit_leg_rows": list[dict]} - the
        verbatim analytics_error_detail display value and the exit-leg
        rows for the selected-lifecycle detail panel. The only function
        that ever surfaces analytics_error_detail.

# 6. UI Layout, Columns, and Behavior

Summary table columns (Trader, Total Lifecycles, Open, Partially
Closed, Closed, Orphan, Unresolved, Invalid, Data Errors, Eligible, Not
Scored, Wins, Losses, Breakeven, Win Rate, Loss Rate, Breakeven Rate,
Avg Return, Median Return, Avg Winner Return, Avg Loser Return) map
directly to `TraderPerformanceSummary` fields; no field is renamed in a
way that changes its meaning, re-derived, or re-rounded.

Drill-down table columns (Lifecycle ID, Symbol, Option Type, Strike,
Expiration, Status, Outcome, Direction, Entry Price, Terminal Exit
Price, Weighted Avg Exit Price, Return, Opened At, Closed At, Ambiguity
Flags, Exclusion Reasons, Data Error) map directly to
`LifecycleAnalyticsResult` fields, with Ambiguity Flags/Exclusion
Reasons joined with ", " (or the em-dash placeholder when empty).

Lifecycle-detail panel: Data Error Detail (verbatim, or em-dash) and an
exit-leg table (Event Type, Consumed Fraction, Exit Price, Sequence
Index), or "No exit events for this lifecycle." when empty.

Duplicate trader names always render as `{trader_name} (ID
{trader_id})`, both in the summary table's Trader column and the
trader-selector's option labels - proven end-to-end with two real,
distinct `trader_id`s sharing the name "TC" in the integration suite
(Section 9).

# 8. Empty-State, Corrupted-Data, and Stale-Selection Handling

    - Missing database: _DASHBOARD_EMPTY_MESSAGE; no file, directory,
      connection, or initialized database is ever created.
    - Database exists, no trader has a current lifecycle:
      _DASHBOARD_EMPTY_MESSAGE (same fixed message).
    - A trader with only not_scored lifecycles: eligible_lifecycle_
      count == 0, every rate/average renders as the em-dash placeholder
      (never "0%"), Not Scored count visibly nonzero.
    - A trader with only data_error lifecycles: Data Errors indicator
      visibly nonzero in the summary row; each such drill-down row
      shows the "⚠" indicator; the verbatim detail is available
      only via the lifecycle-detail panel.
    - Filters remove every drill-down row:
      _DASHBOARD_NO_MATCHING_LIFECYCLES_MESSAGE; the lifecycle-detail
      selectbox is not rendered.
    - A previously selected trader or lifecycle that no longer appears
      (data changed between reruns, or a filter narrowed it out) is
      silently cleared via the session_state-pop-before-render pattern
      - no error, no message, no StreamlitAPIException.
    - Summary/drill-down query or connection failure: the existing
      sanitized log_operation_failure() + fixed-message pattern - no
      raw exception text is ever shown to the user.

# 10. Quality-Review History and Corrections

An independent quality-review pass (separate from implementation)
inspected all five changed files against the approved R8a scope,
verified every checklist item in Sections 5-8 of this handoff by direct
code inspection (not merely by test outcome), and reviewed test quality
for false positives, duplication, brittle indexing, and coverage gaps.
No BLOCKER or MAJOR finding was raised, and no finding indicated any
production-behavior defect. Three MINOR findings were identified and
corrected in `tests/test_app.py` only (no production file touched):

    1. `test_combined_filters_apply_together` originally could pass
       even if the status filter were silently broken, since the
       outcome filter alone already produced the same result under the
       shared class-level fixture. Corrected to use a local
       (non-shared) four-row fixture where status=["closed"] alone
       matches two rows, outcome=["win"] alone matches two different
       rows, and only their intersection yields the expected single
       row - a genuine proof of AND-combination.
    2. `test_summary_order_matches_service_return_order` and
       `test_duplicate_trader_names_render_distinct_labels` had
       byte-identical bodies. The former was corrected to use a local
       fixture returned in deliberately non-ascending trader_id order
       (9 then 2), asserting the displayed order matches - so it can
       only pass if the UI genuinely preserves the service's own order,
       not merely because the fixture happened to already be sorted.
       The latter was left unchanged.
    3. `test_ambiguity_and_exclusion_reasons_visible_in_drilldown`
       asserted only on Exclusion Reasons despite its name; no fixture
       anywhere in the AppTest or integration suites had a non-empty
       `lifecycle_ambiguity_flags` value, so that column's real
       `st.dataframe()` rendering had only ever been proven at the pure
       unit-test level. Renamed to
       `test_exclusion_reasons_visible_in_drilldown`, and a new
       `test_ambiguity_flags_visible_in_drilldown` test was added with
       a local non-empty `lifecycle_ambiguity_flags` fixture, asserting
       the real rendered column content.

All corrections used a local (test-scoped) fixture built via dict
overrides on an existing class-level template - never mutating the
shared class-level fixture lists relied on by other tests. After these
corrections: `TraderPerformanceWorkflowTests` grew from 26 to 27 tests;
`tests/test_app.py` grew from 417/2 to 477/2 insertions/deletions; the
full suite grew from 1321 to 1322.

# 13. Architecture Notes

    - `app/dashboard_formatting.py` is a pure module with the same
      no-database-access guarantee as `database/analytics.py` and
      `database/lifecycle.py` - independently unit-testable with zero
      SQLite or Streamlit involvement.
    - `app/streamlit_app.py` remains the sole orchestration layer:
      it fetches via `TradeService`, formats via
      `app/dashboard_formatting.py`, and renders via `streamlit` - no
      layer does more than one of those three responsibilities.
    - The dashboard consumes R7's read surface exactly as designed:
      `list_trader_performance_summaries()` for the trader-level view
      and `list_current_trade_lifecycle_analytics(trader_id=...)` for
      the lifecycle-level drill-down - no new backend method was
      required or added.
    - The architecture remains modular and provider-independent: R8a
      touches only a new pure presentation module and the service
      layer's existing read surface for lifecycles already computed by
      R7.
